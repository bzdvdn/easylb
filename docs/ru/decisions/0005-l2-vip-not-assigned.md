# 0005 — l2 VIP не назначается на интерфейс

**Статус:** Accepted

## Проблема

Для `l2` VIP speaker анонсирует адрес. Возникает вопрос: не назначить ли VIP на
интерфейс ноды, чтобы ядро отвечало на ARP/ICMP и работал `ping`.

## Ограничения

- Упавший или изолированный speaker не должен оставлять stale VIP на неверной
  ноде.
- Speaker должен сосуществовать с keepalived для других VIP.
- TCP/UDP dataplane уже работает через kube-proxy.

## Варианты

1. Назначать VIP на интерфейс у лидера и удалять при потере.
2. Не назначать VIP; отвечать на ARP из userspace.
3. Добавить userspace ICMP responder для VIP.

## Решение

Вариант 2. VIP не назначается на интерфейс, ICMP не отвечает.

## Почему

- Нет stale-адреса при падении speaker или partition.
- Владение ARP явно привязано к Lease.
- Нет конфликта с ARP ядра для keepalived VIP.
- ICMP echo с source IP, который не назначен, сложно отправить корректно без
  сборки полных IP-пакетов.

## Последствия

- `ping` по l2 VIP не работает; используй ARP/TCP-проверки.
- Часть мониторинга на ICMP потребует альтернативы.

## Когда пересмотреть

Жёсткое требование ICMP-мониторинга или безопасный механизм передачи адреса
на интерфейс с очисткой при crash.
